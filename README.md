# Allegro Hand V5 3F - simulation and unified hand interface

Dissertation code for driving the Wonik Allegro Hand V5 (3-finger) in simulation,
and through the same interface over ROS2.

The claim being tested: one piece of client code can drive different hands - a
9-DOF 3F model, a 16-DOF 4F model, MuJoCo or ROS2 - without modification.

## Layout

| Path | What it is |
|---|---|
| `sim/hand_interface.py` | The abstract contract: joints, targets, efforts, fingers, limits |
| `sim/mujoco_hand.py` | MuJoCo backend |
| `sim/ros2_hand.py` | ROS2 backend (Wonik's JointState topics) plus transports |
| `sim/mock_hand.py` | Mock hand: in-process dynamics, plus an rclpy node |
| `sim/hand_client.py` | Backend-agnostic client. Imports neither mujoco nor rclpy |
| `sim/build_3f.py` | Builds the 3F MJCF from Wonik's URDF |
| `sim/grasp_controller.py` | Force-regulated grasp controller, HandInterface only |
| `sim/grasp_scene.py` | Hand plus object scene assembly |
| `sim/grasp_eval.py` | Grasp evaluation matrix and metrics |
| `sim/bench_dds.py` | Timing benchmark: MuJoCo vs ROS2 loop rates |
| `sim/tests/` | 57 tests. See `sim/tests/README.md` |
| `sim/models/allegro_3f/` | Build output, generated by `build_3f.py` |
| `results/` | Raw evaluation output backing the figures below. See `results/README.md` |

## Setup

### External repositories

A fresh clone of this repo does not build. Two external repositories are
required. Both are gitignored plain clones, not submodules, so they are not
fetched with the repo and their versions are not recorded by git.

```bash
# Required by build_3f.py, which pins and verifies this exact commit
git clone https://github.com/Wonikrobotics-git/allegro_hand_ros_v5-3Finger.git \
    wonik_3f_reference
git -C wonik_3f_reference checkout 40608536f0f2ca43fa78078ebf1a3fd07098427f

# Required for the 4F hand in the grasp evaluation
git clone https://github.com/google-deepmind/mujoco_menagerie.git \
    sim/mujoco_menagerie
git -C sim/mujoco_menagerie checkout da76818   # version used for these results
```

`build_3f.py` verifies the Wonik commit at build time and refuses to build
against a different one. Use `--allow-upstream-drift` to override.

The menagerie commit is not pinned in code. It is recorded here only, which is a
weaker guarantee. Making both submodules would fix this.

### Python environment

Use Python 3.10 if you want ROS2. rclpy ships extensions built against CPython
3.10 (`_rclpy_pybind11.cpython-310-*.so`), so a 3.11+ venv cannot import it.

```bash
python3.10 -m venv sim/venv
sim/venv/bin/pip install -r requirements.txt
```

### ROS2 (optional)

Needed only for the live-DDS tests and `bench_dds.py`. Everything else runs
without it.

```bash
source /opt/ros/humble/setup.bash
```

Required per shell: non-interactive shells do not read `.bashrc`.

The venv can import rclpy and mujoco together even though it is not
`--system-site-packages`. `setup.bash` exports a PYTHONPATH into ROS's
dist-packages, and PYTHONPATH is honoured independently of venv site isolation.
`sim/tests/conftest.py` explains this and its two side effects.

## Build the model

```bash
sim/venv/bin/python sim/build_3f.py
```

Writes `sim/models/allegro_3f/`: the MJCF, meshes, a `manifest.json` recording
input hashes, and Wonik's BSD-2-Clause notice. Rebuilds are byte-identical.

Flags:

```bash
--target-mass 0.890        # different total mass, see caveat 2 below
--allow-upstream-drift     # build against a non-pinned Wonik commit
```

The build checks its own output: 9 actuators, total mass within 1e-6 kg of
target, inertia scaling linear, zero contacts at the rest pose.

## Run the tests

```bash
sim/venv/bin/python -m pytest sim/tests/ -q          # 41 tests, ~2s, no ROS2

source /opt/ros/humble/setup.bash
sim/venv/bin/python -m pytest sim/tests/ -q          # 57 tests, ~16s, adds live DDS
```

Live-DDS tests skip when rclpy is unimportable, so the fast path works anywhere.

## Run the evaluations

```bash
# Grasp matrix: 240 configs (2 hands x 2 shapes x 4 sizes x 3 frictions x 5 offsets)
sim/venv/bin/python sim/grasp_eval.py --spread '3F=0.0,4F=0.6' \
    --json results/grasp_tuned.json
sim/venv/bin/python sim/grasp_eval.py --spread 0.0 \
    --json results/grasp_common.json
sim/venv/bin/python sim/grasp_eval.py --quick        # 4 configs, smoke test

# Loop-rate timing, MuJoCo vs ROS2 over real DDS
source /opt/ros/humble/setup.bash
sim/venv/bin/python sim/bench_dds.py --json results/timing.json
```

## Results

Interface transfer works. The same `hand_client` pose sequence drives MuJoCo and
ROS2 to equivalent trajectories: settled poses agree within 0.072 rad against a
0.10 rad tolerance, per-joint correlation at least 0.923. The same
`grasp_controller` drives both the 3F and 4F hands unmodified.

Two places the abstraction leaks:

1. Timing semantics differ by two to three orders of magnitude.
   `MujocoHand.step()` returns in roughly 0.02 ms, a 50-60 kHz client loop,
   around 100x faster than real time. `Ros2Hand.step()` paces to the publisher,
   100-1000 Hz, matching the publisher rate to three significant figures. Same
   client code, very different wall-clock behaviour, so timing-sensitive logic
   must be written in control cycles rather than seconds. These are wall-clock
   measurements and vary by machine and load; the exact figures behind this are
   in `results/timing.json`, and the ratio is the robust part, not the digits.
   Re-measure with `bench_dds.py` after any change to joint dynamics: removing
   the URDF's placeholder frictionloss took MuJoCo from 7 kHz to 50 kHz on its
   own, by dropping friction constraints from the solver.

2. One grasp parameter does not transfer. The best `spread_fraction` moves in
   opposite directions between the hands, because the same scalar means "oppose
   the thumb" on the 4F and "splay the fingers apart" on the 3F. Retuning it is
   worth 26% to 62% success on the 4F.

Grasp success over 240 configs, force-regulated controller:

| Run | Command | 3F | 4F |
|---|---|---|---|
| Per-hand spread | `--spread '3F=0.0,4F=0.6'` | 56/120 (47%) | 75/120 (62%) |
| Common spread | `--spread 0.0` | 56/120 (47%) | 31/120 (26%) |

The per-hand-spread run is the headline. Grip force in that run: median 13.9 N,
max 35.3 N against a 0.98 N object, with 20% of configs exceeding a 20 N bound.

Both runs are deterministic, so these numbers reproduce exactly. The raw output
is committed in `results/grasp_tuned.json` and `results/grasp_common.json`, each
carrying a header recording the spread setting, controller config, success
criterion and git commit that produced it. If you are comparing your own `--json`
output against this table, check `run.spread_fraction` first: the 4F figure
differs by more than a factor of two between the two runs, and that difference is
the leak described in point 2, not noise.

## Caveats

Detail is in the relevant module docstrings. The short list:

1. Wonik's URDF contains three sets of placeholder values, all with the same
   identical-across-all-joints signature: inertials (every link 0.4154 kg,
   uniform 1e-4 tensor), joint dynamics (`damping=3 friction=10` on all nine
   joints), and probably the 15 N*m effort limit. All three are overridden in
   `build_3f.py` with stated reasoning. The `frictionloss=10` one caused grip
   forces up to 1299 N before it was found.

2. The 1.050 kg target mass is unverified and may be the 4F figure rather than
   the 3F's. See the comment on `TARGET_MASS_KG`. If it is wrong the fix is one
   constant, but every derived mass and inertia moves with it.

3. The meshes are not clean. They have non-manifold edges, and MuJoCo's
   mesh-derived volumes disagree with true triangle volumes by 1.2-6x. This is
   why collision geometry and inertia both come from fitted primitives rather
   than the meshes.

4. Collision primitives cannot represent palm concavity, so all grasp results
   are fingertip grasps. Power grasps are out of scope.

5. The grasp protocol closes in zero gravity, then tests retention under 1 g in
   six directions. The hand is world-fixed with no arm, so an unsupported object
   falls out of the workspace during approach. The approach problem is untested.

6. `RclpyTransport` has only ever talked to our own mock. Topic names and joint
   ordering are read from Wonik's ROS1 source. QoS, publish rate, and whether the
   3F even has a ROS2 driver with this contract are inferred. See
   `sim/ros2_hand.py`'s docstring for the read-vs-inferred split.
